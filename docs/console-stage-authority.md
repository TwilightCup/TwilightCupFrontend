# 控制台选主、舞台只接收

## 当前前端行为

只有 `connectWithAuth` 的控制台入口启用主 T 候选资格；`connect` 默认用于舞台接收。
舞台根和独立场景页均保持接收者。所有页面仍使用各自的
WebSocket、拉流和解码器，不依赖跨机器共享 JS 单例或 localStorage。

已对齐后端 `9b3e91d`：连接声明 `align_client=console|stage` 并在重连时保留，
后端从握手开始固定用途。stage 或未声明用途的连接均不能参选，伪报媒体能力
也不会升级为主。所有连接初始为 follower，只有就绪 console 经后端租约选举
及接管确认后发布 T。舞台不发送 frame_align_status 或 frame_align；本地引擎
仍有不可参选防护，收到错误发布者角色也不会自行成为主。

比赛舞台的 A/B 视频区域只有存在有效主锚点才显示，包括 SEI canvas、普通 HLS
和外部嵌入的回退路径。断线、超时、撤权和服务端 stale 快照都显示等待信号。
不因先前 canvas 有图像继续露出旧画面；收到新主锚点后才允许重新挂载视频。
有新鲜主锚点但暂时缺少本地共同帧时，仍沿用正常解码恢复和安全边界。

## 媒体等待保活

后端在主控制台租约有效但媒体等待时，约每 750ms 发送 frozen=true、stale=false
的保活锚点，T 不变，序号和服务器时间更新。前端将其视为“主仍在线且 T 冻结”，
不误报失联，也不把保活当作本地解码或恢复播放的证明。真正失联的 stale=true、
无主通知和连接关闭仍遮住舞台。

主控制台会收到这些保活回声。同任期的 T 下限上升只更新下限，不撤销已经完成
的接管确认；否则媒体等待时会误用已过期的接管期限发送 relinquish，形成换主
循环。主控制台也不会因收到自己的首个冻结回声而清理解码恢复状态、额外 seek。
新任期仍重新确认，跟随者更换外部权威时仍执行原有解码重建。

## 验证

`npm test` 包含真实 director store 的入口、错误 publisher 授权防护、发包顺序、
候选关闭、超时/撤权/断线遮蔽与恢复测试，并执行实际 MatchScene 模板的两种视频
分支，检查普通视频不能绕过主锚点门控。

额外的只读后端联动测试：

```sh
../TwilightCupBackend/.venv/bin/python -B tests/integration/console_stage.py ../TwilightCupBackend
```

测试从前端目录加载真实前端 store、AlignEngine 和租约模块，将前端连接用途
传入后端 Connection，向本地后端的真实
ConnectionManager 消息分发器发送前端产生的消息。后端源码只读取，不启动服务，
不连接数据库，不写 Python 字节码或 pytest 缓存。模拟独立页面时钟偏移和
0–150ms 的下行链路延迟，覆盖：

| 场景 | 断言 |
| --- | --- |
| 三台舞台先打开、没有控制台 | 无主、没有任何 T 发布、全部等待信号 |
| 随后打开一个控制台 | 控制台当主，三个舞台跟随；模拟 T 偏差在 1 秒内 |
| 单主和两台舞台正常运行时加入第二控制台 | 旧主和 epoch 不变，舞台不中断且不增加 seek |
| 关闭旧控制台 | 新控制台接任，T 单调，舞台在模拟的 2 秒窗口内恢复 |
| 旧主迟到发包 | 后端拒绝旧角色/任期 |
| 再关闭最后一个控制台 | 后端无主，所有舞台等待，不能凭解码能力接管 |
| 主控制台短暂缺帧并收到保活回声 | 角色/任期不变，不因回声增加 seek；媒体恢复后继续播放 |
| 媒体等待超过旧失联阈值 | 保活序号持续递增而 T 冻结，舞台不误判 stale；恢复后继续跟随 |

多控制台接管限于同一个导播账号、同一比赛；所有设备须能访问相同后端和媒体源。
第二控制台需完成媒体准备并成为合格候选后才能接任。正常加入不抢主；接管期间
可能短暂显示等待，不能承诺零间隙切换。模拟传输、媒体和画布不代表已完成真实
多电脑、真实编码流、浏览器 GPU 或 OBS 环境验收，也不证明跨机器像素级同帧。
长时间解码停顿仍可能触发原有恢复重锚；5 秒以内的跟随偏差仍按最高 1.08x
柔和追回，可能需要较长时间收敛。本次不改变该速率策略。
